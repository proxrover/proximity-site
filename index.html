How the work is built

The Proximity Software Factory is the firm's delivery pipeline. Specialist AI agents do the drafting, coding, testing, and review. A human architect approves each stage and signs every release. The pipeline is in use on the firm's own products.

Every stage writes a record: the design, each decision, each test result, and each approval with who gave it and when. A run resumes from its record, and a second run over the same record passes through the same stages and the same gates. The architect of record is accountable for every release.

  1. Design

    The system is split into building blocks, each with a written contract for what it provides and what it consumes. The client approves the design once. The approval is recorded, and the approved design is frozen so that a later change is visible.

    Why: a contract agreed before code means integration is checked against a document, not a memory.

  2. Build

    Each building block runs through its own pipeline. A test agent writes failing tests from the contract, an engineer agent writes code until they pass, and a surveyor compares the result with the design. Blocks build in parallel against stand-ins for each other's contracts.

    Why: no block waits on another, and no code exists without a test that predates it.

  3. Verify

    Three independent reviewers read every change: one for correctness, one for security, one for test coverage. Each finding is checked a second time before it is reported, with the input that triggers it and the fix. A design gate runs before build and a readiness gate runs before release.

    Why: a finding that cannot be reproduced is not a finding.

  4. Prove

    Non-functional targets are written as service level objectives (SLOs): latency, throughput, error rate, availability, and recovery time. Baseline, load, and soak tests run against them, only in a non-production environment the client has approved with a time window and a load ceiling. Each target is recorded as met, missed, or not measured.

    Why: a number measured in a named environment on a named date replaces an adjective.

  5. Record

    Architecture records are generated from the code and its repository, not written from memory. Every sentence in a record cites the engineering rule it rests on, and a checklist gate rejects a record that contains an uncited sentence.

    Why: the hand-over describes the system as built, and it stays checkable after the engagement ends.

  6. Release

    Rollout follows the availability level the client chose, with a health gate at each step and a rollback path. Release notes are written for operators and for API consumers.

    Why: a release is a procedure with a rollback, not an event.

How an engagement works

  1. Scope

    A written statement of the problem, the users, the data, and the interfaces. The Design stage turns it into building blocks and contracts, and the client approves them. Price and schedule are fixed against the approved design.

  2. Build

    The pipeline builds the approved blocks. The client follows progress in the architecture record, which updates as each block moves from drafted to built to verified.

  3. Validate

    The client's acceptance tests run alongside the pipeline's own gates. Non-functional targets are proved in an environment the client names and approves.

  4. Hand over

    The client receives the repository, the tests, the architecture records, the runbooks, and the SLOs, in the client's own accounts and repositories. The firm's pipeline tooling is not required to operate the result.
